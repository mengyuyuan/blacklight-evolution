# 多版本开发、同步与 PR 规范

本规范适用于 Blacklight: Ascension 主仓库及向其提交贡献的 fork。规范的统一入口是主仓库 `main` 的本文件；各维护分支保留一份相同副本。平台配置和安装说明以目标版本分支为准。

## 1. 长期版本分支

| 长期分支 | Minecraft | 加载器 | Java | 维护状态 |
| --- | --- | --- | --- | --- |
| `main` | 1.21.1 | NeoForge | 21 | 活跃开发；主开发线 |
| `forge-1.20.1` | 1.20.1 | Forge | 17 | 活跃开发；独立适配线 |

以上两条线都是开发版，不代表已通过稳定版或多人验收。版本登记见 [versions.json](versions.json)；具体模组版本号、依赖版本和构建命令取自目标分支的 `gradle.properties`、`build.gradle` 与安装文档。

- `main` 当前固定代表 NeoForge 1.21.1，不能因为来了新版本 PR 就替换其运行平台。
- 新增长期分支统一命名为 `<loader>-<Minecraft版本>`，加载器名小写，例如 `neoforge-1.21.4`、`fabric-1.20.1`。这些名称仅是示例，不表示已有支持。
- 同一 Minecraft 版本的不同加载器分别维护。仅模组自身升级、修 Bug 或调整依赖，不新建长期分支。
- 新平台先由维护者确认维护人、起点提交、依赖和验收范围，再建立长期分支并登记为 `experimental`。整套移植 PR 只能合入这条新分支。
- 状态取值：`experimental`（适配中）、`active`（持续开发）、`maintenance`（仅修复）、`archived`（停止维护）。改变状态或新增平台时，同时更新登记表、本规范及有关分支的贡献入口。
- 平台 API、Java、加载器、构建插件、Mixin 配置、网络协议和安装说明各分支独立维护。长期分支不互相整支 merge，也不强制推送改写公共历史。

## 2. 功能分支与 fork

从要修改的长期分支新建临时分支，一个分支集中解决一个问题：

| 用途 | 命名示例 |
| --- | --- |
| 功能 | `feat/neoforge-1.21.1-hive-feeding` |
| 修复 | `fix/forge-1.20.1-held-turning` |
| 跨版本同步 | `backport/forge-1.20.1-pr123-held-turning` |
| 文档 | `docs/neoforge-1.21.1-version-workflow` |

玩法、修复和移植的临时分支（含 `main` 的贡献）写出 Minecraft / 加载器，避免几年后无法判断目标。纯通用文档分支可简化为 `docs/version-workflow-neoforge` 等名称，PR 仍须明确实际 base。个人 fork 可以保留自己的长期版本分支；向主仓库提交 PR 时，base 必须选择主仓库对应的长期分支。

从 fork 开始 Forge 修复的示例（已配置 `upstream` 为主仓库、`origin` 为自己的 fork）：

```bash
git fetch upstream
git switch -c fix/forge-1.20.1-held-turning upstream/forge-1.20.1
# 在此分支实现并验证修复
git push -u origin fix/forge-1.20.1-held-turning
```

在 GitHub 创建 PR 时选择 `base repository: mengyuyuan/blacklight-evolution`、`base: forge-1.20.1`，compare 选择自己 fork 的上述功能分支。不要从自己的 NeoForge 分支直接向 Forge 分支提交 PR。

## 3. 一个版本更新后怎么同步

**按改动同步，不按整条分支同步。** 每个玩法、资源或机制 PR 都要判断其对所有活跃版本的影响；主开发线和适配线都可以先提出修复，不要求所有改动先发生在 `main`。

1. **先完成一个来源版本的 PR。** 说明问题、修改后的行为、涉及的客户端/服务端逻辑，以及其他版本是否受影响。来源 PR 合并后记录 PR 链接和实际合入的提交 SHA。
2. **判断各目标版本。** 同样存在问题或支持同一功能的版本进入同步队列。版本不支持该实体/API、功能本来不同或计划延期时写出原因，不能默认为“都同步了”。纯平台修复可标为不适用；共享文档通常需要同步。
3. **建立一个跟踪 Issue。** 用“跨版本同步”模板为每个受影响版本记录负责人、状态、目标 PR 和验收结果。一个问题用同一张跟踪表；没有跨版本影响时可直接在来源 PR 说明，无须另开空 Issue。
4. **每个目标版本单独开功能分支和 PR。** 从目标分支最新提交开始，引用来源 PR、来源 SHA 和跟踪 Issue。一个 PR 只对应一个目标平台。
5. **适配、验证、合并。** 处理加载器 API、Java、实体、网络和渲染差异。在目标版本独立构建，并如实记录行为验证；目标 PR 合并后更新跟踪表。
6. **按版本分别发布。** 合并和发布是不同状态；记录首次包含该改动的目标版本号和 Release。尚未发包只能称“已合并，待发布”。

同步状态统一使用：`待同步` → `进行中` → `已合并/待发布` → `已发布`；受阻用 `阻塞` 并注明具体原因和下一步，确实不涉及用 `不适用` 并写理由。跟踪 Issue 只有在全部受影响版本已发布、或剩余版本已明确延期/不适用且由维护者确认后才能关闭。

当前只有两个活跃版本时，改一个版本至少判断另一个。未来新增版本后，按登记表扩大检查范围。`maintenance` 版本评估缺陷修复，不默认加入新功能；`archived` 版本不承诺同步。

### 哪些改动能 cherry-pick

- 仅包含可兼容共享逻辑的小提交，可以先查看 `git show --stat` / diff，再 `git cherry-pick -x 来源提交SHA`，保留原作者和来源记录。
- 同一提交混有平台配置、版本号、依赖或不兼容 API 时，逐文件适配，提交说明写 `Backport-of: 原PR链接` 与 `Source-commit: 原提交SHA`，不直接套用整份提交。
- 冲突不能简单选“全部使用来源版本”。保留目标版本的构建配置、Java 版本与加载器接口，检查实际调用和同步路径。
- 合并后产生多个提交时列出实际要同步的提交；squash 合并记录 squash 后的 SHA。不要拿尚未合并的临时分支头充当最终来源。

实际例子：NeoForge PR #5 的抓取转向修复通过 Forge PR #7 单独适配，保留 Forge capability 访问和 Java 17 的数值夹取实现；没有把整套 NeoForge 平台复制过去。

### 优先级与同步节奏

导致存档损坏、物品丢失、崩溃或核心操作失效的修复，优先同步到所有受影响的维护版本，并作为这些版本下一次发布的验收项。普通功能可以分批上线；记录缺口和负责人，不强制为了等待某个适配版本而阻塞其他已验证版本。

客户端/服务端都涉及的改动需同步相关两端逻辑。不能只迁移客户端动画而漏掉服务器裁定，也不能因“代码一样”就省略目标平台构建。不同 Minecraft / 加载器版本不保证互联；同一服务器应使用匹配的游戏、加载器、模组和依赖组合。

## 4. PR 必填信息

使用仓库 [PR 模板](../.github/pull_request_template.md)。玩法、修复和移植 PR 的标题写明目标，例如 `[MC1.20.1 Forge] fix: 持有生物时自由转向`；通用文档 PR 可用 `docs:` 标题，在正文明确 base。

- Minecraft、加载器、Java、目标 base 分支。
- 问题、触发条件与修改后行为。
- 来源 PR / SHA / 跟踪 Issue；首次实现写“无，首次实现”。
- 对其他维护版本的影响、同步计划或不适用原因。
- 实际执行的验证、产物及未验证项；已有失败不能标成通过。
- 涉及模型、动作和特效时提供可编辑资料、导出结果、资源来源及现有截图/视频或尚未试玩说明。
- 涉及协议或存档格式时说明兼容策略、迁移/回退条件。无法向旧格式回退的变更不能宣称随意回滚。

维护者合并前必须核对 base 分支和 diff。仅修复一个问题却出现大量加载器替换、动作删除或配置重写时，先纠正提交范围再合并。全平台移植应明确标为移植，目标是新版本分支。

## 5. 验证与合并条件

| 改动 | 要求 |
| --- | --- |
| 纯文档/模板/版本登记 | 核对链接、平台数据、示例和同步副本；不需要为文字修改新增单元测试 |
| Java 或构建改动 | 使用目标版本的 Java / Wrapper 编译打包，目标 PR 的 CI 通过 |
| 动作/模型/贴图 | 保留可编辑资料，核对成品资源、对应清单及已完成的实际效果验证 |
| 网络/服务端机制 | 检查两端读写、实体生命周期和兼容要求；未运行专用服务器或多人验收时明确列出 |
| 正式稳定版 | 按目标分支发布清单完成运行、玩法、存档和联机验收；不能只凭 assemble 或来源平台测试放行 |

普通构建与当前 CI 只执行 `assemble`。单元测试、碰撞测试、GameTest 和游戏内验收按用户明确要求执行并记录；没有执行时填写“未验证”。正式版本需要补齐发布验收，开发预发布保留未验证项和已知失败。

当前没有自动同步机器人，也没有强制校验 base 平台或跨版本完成状态的 CI；模板、跟踪表与合并审阅承担这部分检查。不得把写了同步计划当成已自动移植。

## 6. 版本号、资源与发布

- Minecraft 版本、加载器和模组版本是三项独立信息。NeoForge dev.8 与 Forge dev.3 可以同时存在；相同主版本号不表示能力和进度完全一致。
- 每条线独立提高开发版/正式版号，写出新增、同步内容与未同步内容。共用玩法设计编号可以引用来源 PR，不能用相同 dev 数字伪装进度一致。
- 新发布的标签和安装包名称应能辨认 Minecraft、加载器和完整模组版本；不得复用同一个 tag 覆盖另一平台，也不重写历史 Release / tag。具体文件名以该分支的真实构建产物为准。
- Release 必须由对应目标分支的提交生成，注明提交 SHA、依赖、安装说明、验证范围与文件校验值。Forge 分发重混淆后的安装 JAR，不把 slim 中间产物当安装包。
- 共用动作、HUD、镜头或源模型只同步该改动需要的文件；保留资源来源说明，重建相应清单并核对目标成品。不要恢复过期模型、删掉现有动作或仅改文件名来“兼容”。
- 各版本独立实例、配置和测试存档。降版不承诺存档可读；涉及迁移时先给出明确方案并保留备份。

## 7. 分支清理与规范维护

临时分支仅在 PR 已合并、提交完整进入目标长期分支、没有其他未合并 PR 或未保存工作依赖它时删除。保留 PR、提交、Release 和长期版本分支；不用永久 `feat/*`、`fix/*` 保存已经完成的版本。

清理前重新核对远程分支头，避免删掉合并后新增的工作。本地被运行客户端或 worktree 使用的分支先保留；不要为了清理 GitHub 分支而删除用户存档和工作目录。

规范、版本登记和模板的通用变更先合入 `main`，再以仅含这些文件的 PR 同步到其他维护分支。各分支的 CONTRIBUTING / README 都链接本规范；分支特有的安装和开发环境段落保留各自内容。新增版本时必须把规范副本和模板一起接入。
