# 原作风格地面载具、车队与车库设计

任务起始日2026-10-25；现场依据更新至2026-10-26。状态：研究及待实现设计。本文不是车辆已经实装或测试通过的声明。

## 1. 目标与当前边界

在军方与黑色守望现有步兵、编制、基地和有限弹药体系上，增加运输卡车、装甲输送/战斗车与坦克。两方各有涂装，车辆可组成真实乘员驾驶的AI车队，接受军官指挥，在已加载的道路上巡逻、交战、清剿合法感染目标并回基地补给。玩家可以正常驾驶空车、使用车载武器，也可以像Prototype主角一样抢夺AI载具。

用户已把具体细节交给我们决定，并明确驾驶、操作武器和抢夺都在范围内。先结束military.5的当前验证，再按独立阶段制作载具，不用新范围阻塞前一版收尾。

- 本阶段不改变军方/BW当前同盟关系、平民身份或感染目标政策；这些以原作者与用户后续决定为准。清剿复用当前合法敌人规则。
- 不引入大型枪械/载具模组依赖；继续原生Java实体、现有枪械物品库和可编辑MC低模。
- 首套包含地面三类底盘、两方涂装、玩家/AI驾驶、炮手、抢夺、有限资源、车队、车库和保存恢复。直升机、飞行物理、水陆两栖、真实悬挂、弹道穿深和大型任务剧情另列后续。
- 用户亲自拉取的“模组1.2.1标签”尚未核验。这里以实际Neo MC1.21.1/Java21及Forge MC1.20.1/Java17工作树设计，不fetch/pull/merge该标签，不承诺未经验证的兼容性。
- 所有速度、耐久、弹量、比例、距离和时间均为**本模组拟定平衡值**，不是《虐杀原形》原作数值、现实武器数据或真实军队编制。

## 2. 现场核查与可复用部分

详细依据见[研究记录](../../verification/PROTOTYPE_VEHICLE_REFERENCES_20261025_ZH.md)。当前没有已注册的卡车、APC、坦克、车辆炮弹库存、车库维修、驾驶包或抢车状态机。

现有八枪七弹可以继续作为人员武器库；`MilitarySoldier`已经有限备弹、换弹和乘坐时停止个人战术AI。现有`FirearmsCombat`却要求LivingEntity，并从眼位发射；`OrdnanceProjectile`按Kind找武器，不能区分同类的不同炮弹；因此不能简单给士兵加大模型就声称完成车辆。

结构骨骼采用`root → body → turret_yaw → gun_pitch`，另有轮组/履带、`door_*` / `hatch_*`；各`seat_*`、`exit_*`和`muzzle_*`以命名挂点及 Blockbench 空组保留。底盘独立前进/转弯；炮塔按炮手朝向转动并有角速度限制；开火有小幅炮管后座、炮口闪光和烟尘；动作先保证位置正确，不做昂贵逐片履带模拟。

采用一份本地authoring JSON记录块状几何、贴图布局、骨骼与座位/炮口锚点，生成可打开的`.bbmodel`、客户端模型资源和服务器挂点配置。模型与服务器炮口不能各写一套无关联坐标。玩家第一/第三人称、乘员握持/坐姿、炮塔俯仰与碰撞边界都须用实际加载的MC资产观察。

M6 已生成的作者入口为 `art/military-vehicles/vehicle-authoring.json`，脚本为 `tools/build_military_vehicles.py`；客户端 `assets/blacklight/military/vehicle-models.json` 含原生 ModelPart 可消费的 `parent/pivot/box/uv`，服务端 `data/blacklight/military/vehicle-mounts.json` 同源生成。作者坐标 X 右、Y 上、Z 车头、地面中心为原点；客户端是父骨骼相对坐标乘 16，并保持 Y 上，不套 Humanoid 的翻转或 24 像素偏移。两涂装 PNG 全部由原创色板生成。离线生成和几何预览不构成 Blockbench GUI、GL、驾驶或客户端验收。

模型验收不是一张AI概念图。每车须有军方/BW两涂装的正、侧、前斜、后舱与驾驶视角，另有带乘员、炮塔转向/俯仰和受损状态；交付源文件、实际资源路径、生成命令、哈希与游戏截图。在资料里逐条写“画面观察到的原作形态→本模组哪组几何/纹理/动作落实”。未目视的特征写待核对。

## 4. 实体身份与模块边界

### 4.1 采用独立Entity

采用`MilitaryVehicle extends Entity`，用真实`MilitarySoldier`乘员提供AI司机、炮手和军官。车辆有自己的耐久、库存、座位和控制逻辑，属于机械目标。

不继承Mob只为套用步行寻路或眼位枪械接口。当前感染、吞噬、伪装和抓取围绕LivingEntity/Mob构建，车辆若变成Mob，会被当作可感染、可吞噬或可伪装的人形目标。独立Entity能保留身份边界；仍添加明确机械目标判定及测试，不能只靠体型碰巧躲过。

代价是需要专门的车辆移动、伤害桥、乘员同步和AI路径。这个代价可控，而且避免为了复用接口扭曲目标身份。

### 4.2 领域接口

| 模块 | 拥有的数据/职责 | 禁止承担的职责 |
| --- | --- | --- |
| `VehicleCatalog`/`VehicleDefinition` | 底盘尺寸、挂点、座位、武器、平衡与版本化配置 | 不生成物品或免费初始化库存 |
| `MilitaryVehicle` | 唯一实体UUID、实际库存、耐久、燃料、乘员、姿态和落盘 | 不扫描全维度实体；不伪装成生物 |
| `VehicleSeats`/`VehicleControlAuthority` | 实际乘员到座位、控制租约、服务端输入、原子换座 | 不信任包内玩家身份或客户端位置 |
| `VehicleKinematics`/`VehicleHullShape` | 有界移动、碰撞、转弯与支撑检测 | 不用士兵路径是否可走代替车辆可通行 |
| `VehicleAttackService`/`VehicleDamageBridge` | 真实炮口、射手、机械伤害、现有权限接入 | 不绕过玩家保护、不调用吞噬整车 |
| `VehicleThreatBridge`/机械目标Goal | 把现有合法敌方乘员/射手对应到实际机械车体，支持NPC攻击车辆 | 不用`Mob.setTarget`硬塞Entity，不把所有空军车变成新敌人 |
| `VehicleHijackSystem` | 排他抢夺、真实乘员移交、取消清理、控制权转移 | 不另造第二套Consume收益/身份逻辑 |
| `VehicleFleetSystem`/SavedData | 车队成员、人员单位关联、任务、故障与有限调度 | 不把车当士兵扩充人员编制上限 |
| `VehicleGarageService`/Data | 已注册车库、真实库存、维修、有限派发与损失记录 | 不把任何箱子/绿色建筑自动认证为车库 |
| `MilitaryBaseAccess` | city包提供只读基地是否已加载、归属、核心、位置与人员入口 | 不暴露可被车辆模块任意改写的基地内部Map |

网络、注册与客户端层分别适配Neo和Forge；纯规则与数据结构保持一致。新增数据有schemaVersion与校验，不直接保存运行时枚举ordinal作为永久协议。

| 自动炮弹 | 伤害8、6tick间隔，低半径破片效果，适合普通感染体与轻型机械 | 单发真实消耗，最大作用距离96格 |

| AP主炮 | 对机械主命中36伤害，低范围碎片；对其他目标按统一保护处理 | 是游戏化装甲系数，不做真实穿深/贯穿模拟 |

载具存在机械装甲系数，普通步枪对重装车伤害低但不负数；爆炸/AP更有效。拟定矩阵按轻型/装甲/重装依次为：普通子弹1.0/0.25/0.10，自动炮1.0/0.70/0.30，HE与火箭1.0/0.75/0.50，AP为1.0/1.0/1.0。适用重型超能力沿用实际伤害后再走明确机械倍率，不因机械标签自动变0。倍率集中在同一配置且可测试，不散落每把枪/每个载具。过热、复杂弹链和逐件装甲破损不纳入首套。

燃料用有限`military_fuel_can`物品补充，一罐增加120秒移动预算，到上限即停止领取。只有实际运动/受阻持续给油时按规定消耗，不因停在车库就免费补满。零燃料停车，炮塔和已有弹药仍可手动使用。维修零件每件恢复20耐久，只在真实维修位使用，不能复活已销毁实体。

自然派发只给一次明确写入槽账本的初始资源。物品放置或创造命令测试生成的空底盘，默认弹药和燃料为零；独立测试命令可显式选择带初始库存并在输出写清。重登、换座、抢夺、换归属都不刷新资源。

### 5.1 生存获取

新弹药、燃料和维修件提供普通工作台配方及JEI可读取的标准recipe JSON，不依赖JEI才能制作。拟定批量：自动炮弹每铁锭+铜锭+火药制8；HE每2铁锭+2火药+铜锭制1；AP每3铁锭+火药+铜锭制1；燃料罐每4煤+2铁锭+玻璃瓶制1；维修件每2铁锭+红石制1。这是MC游戏配方，不描述现实军火制作。

空底盘按运输卡车→装甲车→坦克逐级制作：卡车消耗6铁块、2铜块和熔炉；装甲车消耗1空卡车底盘、6铁块、红石块和侦测器；坦克消耗1空装甲车底盘、6铁块、红石块和发射器。均为9格以内标准配方。只接受全新空底盘物品，不将已经放置且有库存/乘员的车辆当作可被配方复制的材料。首套不做收纳整车到物品、自动工厂或无限基地生产线。

配方与战利品供应表一起记录在资料卡，两个版本使用各自实际支持的recipe格式。库存罐/弹药不因打开箱子刷新，创造模式获得物品也不能改变普通生存的扣弹规则。

玩家可在车停稳时近距离用实际持有的匹配弹药/燃料补给，不要求先造车库才能让空底盘行驶；维修仍要求有效维修位。基本车辆菜单显示座位/弹种与库存，补给/取出都由服务端验证距离、真实物品、速度与访问权限后转移，不能通过客户端菜单数值增弹。普通右键上空席，潜行交互或独立可重绑定动作打开菜单，避免强占已有枪械换弹输入。

## 6. 地形、碰撞与驾驶

MC默认EntityDimensions通常只有一个水平width，不能直接表达长车。实现必须区分：车身局部有向矩形/盒体、转到世界坐标的保守AABB、实际选取/受击用的局部盒体。保守AABB用于原版碰撞和区块查询；局部盒体用于座位/炮口/交互，不通过缩小碰撞箱让长车穿墙。保守箱在对角狭道可能偏严格，明确记录此限制并设计合理道路，而不是承诺完整物理模拟。

- 服务端进行扫掠移动，单步不超过0.25格；转向检查起止yaw之间的完整旋转包络，不只检查最终姿态。按车角弧长不超过0.125格分段，以带弧线误差膨胀的每段保守盒覆盖中间姿态，车身与炮管不会从薄墙/门柱中转过去；安全后才允许新yaw。
- 首套可过1格缓坡/完整台阶，限制陡坡、深水和侧翻风险；全轮/履带支撑采样，不让车头悬空时继续当作平地走。
- 不加载未知区块，不跨世界边界，不自动碾碎建筑作为脱困方法。未知/阻塞路径安全停车并报告原因。
- AI路径节点按车身通行宽度、转弯半径、地面高度与可停靠区校验；步兵可过的窄门不表示车可过。
- 撞普通实体伤害如启用，经过同一射手/友军/玩家保护校验并有逐目标冷却；首套默认不主动冲撞友军，不把撞人作为寻路。无驾驶员滑落仅有环境伤害，不能冒充远程玩家攻击。
- 驾驶输入WASD、原版下车键，炮手使用视角瞄准；开火使用可重绑定的主/副开火动作。换座和弹种选择在简单座位/武器界面与可重绑定动作中提供，不能写死覆盖已有超能力按键。
- 单人司机在炮手席空置时可使用武器；炮手真实占座后，武器只归炮手。指挥官席不产生第二名司机，也不自动多开一门炮。
- 玩家第一人称使用座位相机与合理挡风/炮镜遮挡，第三人称沿用可切换视角。HUD只显示本车耐久、真实燃料、选中武器弹量、座位和失效原因。

## 7. 服务端控制权与真实乘员

`VehicleControlPayload`只发送实体UUID、控制租约、单调序号、限幅输入、瞄准与动作位。服务端从连接上下文取玩家，逐次验证同维度、车辆已加载、真实乘坐关系、座位权限、当前租约、递增序号、有限角度和射速。绝不接受客户端位置、血量、弹量、命中或阵营判断。

控制状态只在主线程改变，座位与租约同步原子完成。10Hz输入即可，最多20包/秒；5tick无新输入则松油门制动，断线/死亡/下车/换维度立即撤销旧租约。新司机换新租约；旧包不能继续发炮。服务端炮塔旋转限速，客户端插值只负责显示。

AI司机/炮手必须是本车真实、存活、同维度且处于正确座位的士兵。司机/炮手/车长是可变座位工作job，与现有`MilitaryRole`和军衔分开，不为上车再增加无必要的军衔枚举。没有司机即停车，没有炮手且没有有权玩家即不自动开火。已有`MilitarySoldier.tacticsAvailable()`阻止乘员重复个人步枪AI；车辆另用窄的`crewOperational`检查排除死亡、感染、NoAI、眩晕、被抓/被吞噬等状态，不能直接复用必然因isPassenger返回false的步兵方法。乘员库存、单位、军衔与归宿保留，不复制一个隐形炮手。驾驶坐姿只调整显示，不借隐藏枪械而清空/补发其真实主副枪。

车辆与乘员采用原版实际骑乘保存。只保存座位到乘员UUID的索引，不在车辆NBT再次嵌套复制一份士兵，也不保存/重建玩家实体。恢复时与实际加载的乘员对账：缺席不会凭UUID生成新士兵，重复座位拒绝，失效玩家预留有界清理。进新进程不恢复按住的输入或旧控制租约。

## 8. 抢夺AI载具与吞噬乘员

普通玩家可登空座位。强行夺取有AI乘员的驾驶席，默认需要当前模组已成立的感染/原型能力状态及服务端允许；不要求新增一套“驾驶技能”。默认只强夺纯AI占用车辆；已有真人司机、炮手或会被本次驱逐的真人乘员时拒绝强夺，避免未经设计扩展PvP。空余座位仍按正常规则处理。

抢夺状态为`VALIDATE → CONTACT/EXTRACT → COMMIT`，可随时进入`CANCEL`。车辆、玩家、目标乘员各有唯一排他锁，开始前、动作每tick和COMMIT前都核验真实车辆、席位/原目标或已确认的提取结果、约3格触及范围、实际舱口/外部抓握点、视线、忙碌/抓取状态与世界边界；不允许隔墙隔区块发包抢车。车辆驶离、玩家退开、遮挡或其他控制者改变席位时立刻取消；进行中的接触可有有限制动，但不远程瞬移/锁死整辆车来维持假接触。驱逐动作先用约30tick的简单接近/拉出；吞噬必须等待现Consume session的真实成功结果，不能计时到30tick就擅自结算。不给远处传送或无敌。

外拉驱逐与吞噬驾驶员分开：

1. **驱逐存活乘员**：原乘员作为同一UUID实体从安全出口离车，保留耐久、装备、弹药、军衔、单位和驻地；附近可按当前敌人/警戒逻辑反击。没有合法安全出口则延期/取消，不把人塞进实体方块。
2. **吞噬该乘员**：在`ConsumeSystem`添加窄入口接收已验证的车辆、座位和真实目标，继续同一Consume session、血量/Assimilation门槛、排他抓取、收益和清理。不能把现有“所有骑乘者不可吞噬”整体删除，也不能直接在车辆代码加生物质或复制身份。
3. **提交控制**：旧AI任务与炮手控制全部撤销；需要清除的敌方原乘员真实离座或完成吞噬。玩家实际成功占驾驶席后签发新租约，原UUID/耐久/燃料/每种弹药/装填冷却原样保留。不得先销毁再生成一辆满状态复制品。
4. **暴露与归属**：通过窄的公开`DisguiseSystem.vehicleHostileAct`事件接入现有目击暴露；不是全地图无条件曝光。伪装成军官不授予服务端编制、车库或管理命令权限。原生基地归属永久保留；玩家占有和当前控制者独立保存，基地不能远程强制收回玩家控制。
5. **取消与故障**：玩家离线/死亡、目标死亡、车辆毁坏、世界变化或超时都释放锁并停止旧输入。已发生的真实伤亡不回滚复活；若吞噬已完成但上车失败，玩家留在车外，不生成替身司机。

车辆自身永远不是Consume目标、感染宿主或伪装身份来源。“吞噬司机”不等于吞吃整辆车。

## 9. 真实炮口、炮弹与伤害权限

新增`VehicleAttackService.fire(vehicle, actualActor, weapon, shotMount)`，把机械承载者与实际射手分开。射击上下文包含车辆/实际射手、同维度、实际控制租约、武器ID、炮口世界坐标与方向。炮口由authoring挂点按车体yaw、炮塔yaw与炮管pitch计算；发射前检查炮膛到炮口是否被墙或本车挡住。可信模型挂点明确哪些炮管/发射口属于正常出膛通道，其余本车装甲仍阻挡，俯仰限制防止对自身车体发炮；不能把“忽略本车”无限放宽成任意车身穿透。不能从士兵眼位发出坦克炮，也不能从墙后伸出的枪口穿墙射击。

- 射手是实际玩家或真实AI炮手，不是“车”假冒的LivingEntity。玩家操作炮击必须经过该玩家的方块/实体保护权限；NPC使用现有mobGriefing与事件规则。
- 对有真人乘员的车辆，玩家攻击还要检查服务端PvP、canHarmPlayer与既有保护；PvP被禁止时不能靠先打机械外壳再伤害乘员绕过。NPC针对合法敌对玩家的行为继续按现有NPC规则，不把PvP开关错误扩大成玩家对所有怪物免疫。
- 新`VehicleOrdnanceProjectile`保存明确武器ID、发射时实际射手UUID/维度、原车辆标识及有界寿命。按Kind找第一把武器的旧逻辑不扩展到车辆。
- 射击先验证目标/炮口/库存/冷却，再在一次服务端动作里真实扣一发和生成弹体；生成失败仅撤销尚未生效的本次扣弹。客户端不能请求“命中某人”。
- 弹体命中时射手若已经死亡、消失或跨维度，不造成幽灵伤害；离车后仍在同世界存活的正常已发射炮弹可飞到命中，归责保持发射时射手，不切换给新司机。后续旧司机输入一律拒绝。
- `VehicleDamageBridge`让现有子弹射线、爆炸和适用超能力在受保护前提下命中机械Entity。当前只遍历LivingEntity的攻击需要显式增量接入，不能仅实现`Entity.hurt`就声称现有所有能力都能打车。
- 车内关闭舱门的乘员不被同一外部子弹重复结算成车体伤害加全员伤害。开舱/真实外露乘员按实际命中处理；毁车后依规则对真实乘员造成有限伤害并安全离车。
- 方块破坏复用M5玻璃/软材/硬材、容器保护、已加载范围与事件规则；每次爆炸候选有上限，不无界递归、连续生成区块或免费恢复建筑。
- 车辆毁坏只结算一次。剩余物资按配置实际掉落/销毁，保存过的损失账本禁止同一原生槽再发车；不把掉落和一辆满库存新车同时给出。

独立Entity还需要**机械威胁目标桥**，只有受伤接口不够：当前`MilitarySoldier.validTarget`、`BlacklightHunter.beginAttack`与`CombatTargeting`等以LivingEntity为目标，直接沿用会导致感染体追乘员却永远不打车。新增`VehicleThreatBridge`持有“真实车体+当前规则合法的敌方乘员/已成立敌对射手”上下文，提供车身表面距离、可见命中点和有限目标有效期。现有士兵/感染者通过窄的机械目标Goal移动和攻击实际车体，不将车辆强转成LivingEntity，不绕过既有伪装/友军/玩家保护。关闭舱门保护的是乘员，不使整车免疫现有敌对AI；空车默认不成为新的主动生物敌人，已有伤害引起的反击沿当前事件规则处理。核心感染体的适用近战/范围攻击逐一测试，不承诺仅加`Entity.hurt`便自动兼容所有第三方怪物。

## 10. 步兵武器组合

兵种/军衔与武器分别建模。普通兵可以持步枪、卡宾、机枪、榴弹或火箭筒，不需要为每把枪再创建一个士兵实体类型。初始化按任务角色或配置权重一次决定，之后落盘，绝不每tick抽取/补弹。

| 生成场景 | 拟定默认组合 |
| --- | --- |
| 8人常规巡逻 | 1卡宾队长、5步枪、1机枪、1支援；支援默认榴弹 |
| 8人重型清剿/已确认机械威胁 | 保留上述结构，支援换火箭筒携带者 |
| 12人加强巡逻 | 1卡宾队长、8步枪、1机枪、1榴弹、1火箭筒 |
| 其他独立生成军方，配置权重 | 步枪65、卡宾15、机枪10、榴弹6、火箭4 |
| 其他独立生成BW，配置权重 | 步枪60、卡宾18、机枪12、榴弹6、火箭4 |

比例只用于一次生成与任务编成，不改变原有军衔任命。有限发放遵循实际库存：步枪维持30+90、机枪60+180；榴弹6+12；反装甲兵配卡宾24+48与火箭1+2。主/副武器都是实际ItemStack，按弹种各存备弹，不能在换武器时把原单个`ammunitionReserve`数值自动兑换成更贵弹药。

独立生成的权重池只作用于普通火力配装；现有重装实体默认机枪、军官/指挥官默认卡宾，不被普通池随机改没。显式任务可覆盖为反装甲/特殊支援角色，但仍必须实际发放对应有限物品；军衔、装甲外观与当前座位工作独立。

旧档迁移只把一次原备弹映射到原来实际武器弹种，保留原枪膛余弹；没有武器或失效物品不制造补偿枪。导弹、温压武器只在明确任务/补给库存中发放，不进入普通随机巡逻；感染发射器不自动发给两方士兵，避免擅改阵营政策。

爆炸武器必须有合法目标、足够安全距离（拟定10格）、友军/受保护实体与路径检查，近距离改用实际携带副武器。车辆/重型感染目标可提高反装甲优先级，不能给所有步枪兵无限火箭。

## 11. 车队、军官与清剿

车队数据记录自己的UUID、真实车辆UUID、真实人员单位ID、指挥官UUID与任务。现有班排连/中队大队仍拥有人员；车队以关联关系接受命令，不额外把每辆车计成一个人。

首个默认车队为装甲车前导、卡车居中、坦克后卫，1–4辆也可独立成队；更大规模用多个车队接受上层协调。保持约8格行进间隔、14格战斗/停车间隔，按最慢有效车辆速度走。座位上限不是必须满员：三车最低配置为卡车1司机、装甲车司机+炮手、坦克司机+炮手+指挥官，共6名；余下运输兵从现有人员中按任务选择。乘员必须从既有真实人员中分配，车队不额外创造19个免费士兵，也不要求军方16人基地凭空填满19席。

任务用独立`FleetMission`表示`GUARD/PATROL/CLEAR_AREA/RETURN`，映射现有人员命令；不要随意在已保存的`MilitaryOrder.Mode`中插入新枚举而破坏旧档。军官下令，司机负责车体，炮手负责武器；士兵可在安全停靠后按命令真实下车搜索。

指挥官死亡/失联时，先保留现有正式任命，运行时由当前已加载且有效的最高军衔者临时代理，同级按UUID确定，避免每tick变人。无有效代理则停车防御/按最后有效返程点撤离，不继续无指挥冲进未知区块。玩家占车不被AI命令强制夺回驾驶。

清剿只锁定当前目标规则允许的感染者，使用局部已加载搜索（拟定32格）和现有视线/伪装/友军保护。任务结束写局部接敌/目标结果，不擅自把整个城市感染度清零或宣称城市永久安全。

独立车辆工作预算：全维度每tick至多2次路径规划，同车至少间隔20tick；单次搜索半径96格、节点2048上限，轮转公平；不抢占现有步兵`MilitaryWorkBudget`。出发前核验宽路/转弯/加载；路径失败达到3次或持续100tick后进入`BLOCKED`，安全停靠并报告，而不是每tick重搜或强行拆墙。默认原生车队自动激活预算每维度12辆，可配置0–64；远处自然暂停，不强加载整条城市道路。

## 12. 车库、补给、损毁基地和有限派发

现有13×13露天标线垫不是功能车库。新增拟定31×27×9车库附属结构，三条约7×12车位/维修线、6格以上宽入口、5格以上净高、露天进出院与弹药/燃料/零件库。坦克炮管与转弯需进实际验证。

车库由真实结构注册数据+坐标范围+核心/基地关联+指定容器/维修位共同认证。建筑外观或放一个箱子不自动产生派发名额。用独立StructurePiece、蓝图元数据和地形边界，不能给旧65格基地偷偷扩大范围并覆盖玩家建筑。

新自然生成基地只有在附属范围测地形和道路成功时生成/注册车库；失败则保留原基地并输出未设车库状态。已有世界只通过明确的管理员选址/预览命令附加，先展示占地/冲突，不自动翻新旧世界。

- 每个有效新车库默认只有卡车、装甲车、坦克各1个**一次性初始派发槽**，不是永远补满3辆的上限。初始库存、车辆UUID、出厂状态写入数据后才视为已派发。
- 人员从既有16/20有限人员槽中已存在且适合的士兵分配；没有空闲真实司机/炮手则等待，不新增人员上限，不覆盖用户明确编组/命令。
- 车辆尚未加载、被玩家开走、被抢或已毁坏，都不能按“附近没找到”重发。同一UUID的未知/卸载状态先保留；损失是永久账本。
- 后续补充可以把玩家真实制作/运入的车辆登记为驻车，不会凭名额凭空制造底盘。车库扩建不清空旧损失或重复初始化。
- 领取弹药/燃料/维修仅在车体完整停于有效维修位、容器已加载、实际基地允许时进行；按正确物品逐件扣除后增加实际库存，余量不够就按真实数量领取。拆箱或换区块不会补回物品。
- 驻地核心失效会停止新车派发和该处自动维修；在外车队仍保存原归属并可独立交战、前往另一处**已加载且同阵营、有效、有道路与资源**的车库。找不到时建立野外停靠点，不瞬移、不跨维度找油、不远程取箱。
- 玩家控制优先；基地损毁不把正在驾驶的玩家拉回，不重置其HP/炮弹。车辆原生基地、当前驻地、玩家占有、当前车队分别保存。

## 13. 保存、旧档与失效处理

以车辆实体NBT的实际HP、燃料、物品库存和武器冷却为资源唯一来源；Fleet/Garage SavedData只索引身份、任务、归属、槽与损失，不复制一份可被重载加回的库存。保存schemaVersion、底盘/涂装ID、实际乘员座位、origin/current home及维度、占有与车队ID；不保存旧输入租约、路径节点缓存或未完成的客户端动画。

跨文件初始化使用明确的未发/已保留UUID/已发/已损失状态；崩溃恢复遇未知实体不重发。承认原版世界多个文件的持久化并非数据库事务，测试至少覆盖正常两进程重启和有界的中断恢复，不能宣称任意磁盘故障下强事务保证。

旧M5档没有车辆字段时读取为空集合、不发车、不修改原人员归宿或基地核心。新增车库需显式生成/登记。缺失车辆配置或无效武器ID进入停用并报告，不能回退为另一辆满弹坦克。版本升级前备份世界，两个加载器分别做旧档迁移和实际停服重启验证。

## 14. 验证与交付标准

每阶段执行RED→GREEN：先写与生产入口一致的失败用例，确认因缺少规则失败，再实现最小规则，执行同一验证通过。纯规则使用JUnit；Entity/世界/网络/保存使用实际GameTest或独立服务器；模型和驾驶用真实客户端验收。不能只对复制出来的测试模型自证正确。

| 必测场景 | 合格结果 |
| --- | --- |
| 原作参考与实际资产 | 三类车真实目视记录、两涂装、源文件、游戏多视角；不能用概念图冒充成品 |
| 7格门、9格路、转弯、台阶、坑/水/狭门、未加载边界 | 可通处通过，狭道/未知安全停车；车身不穿墙、不强加载 |
| 玩家驾驶/炮手/单人操作、换座/离线/维度变化 | 唯一有效司机/炮手；旧包和超速/NaN输入不能移动或射击 |
| 真炮口、挡炮口、弹种/冷却、友军/权限、普通枪与能力打车 | 无眼位炮、无穿墙与权限绕过；正确机械伤害，无吞噬整车 |
| 已有合法敌人的实际士兵/猎手等攻击有乘员载具 | 能在车身表面攻击并降低车体耐久，不追不可达座位空挥，不新增空车敌人政策 |
| 两玩家同时抢AI车、重复/延迟包、目标死亡/离线 | 一次控制转移、一次真实乘员结果；无克隆、满血满弹或幽灵炮手 |
| 抢夺含真实消耗、驱逐/吞噬、伪装/目击 | 复用现有收益/门槛/警戒，不越过PvP默认边界 |
| 车辆弹药、燃料、维修和盒子不足/被拆 | 增多少扣多少，空了就停，重登不返还 |
| 指挥官死亡、车队远离原基地、失效基地/别处车库 | 可代理与野外作战/返程；不重发、不瞬移、不强加载 |
| 旧M5档/新车档真实两进程重启 | UUID/HP/余弹/冷却/损失/真实乘员正确；旧档不自动铺车库 |
| 有界压力：3、12、24辆+原步兵，两个加载器 | 规划计数不超预算、输入延迟与tick耗时实测记录；不编造硬件无关FPS |

交付须保留实际命令、时间、环境、失败及修复证据，更新兵种/车辆/弹药/建筑数据卡和易懂测试流程。military.5的已验证结果单列，载具结果不借用旧版测试冒充。之后用户拉好模组1.2.1再现场核对差异，按该版本真实API适配和重新验证。

## 15. 阶段与唯一下一步

1. 在M5完成后冻结已验收版本；先补真实原作画面记录，建立独立车辆领域/持久化内核与可编辑模型源。
2. 车辆碰撞与真实席位→玩家驾驶/武器→伤害桥→抢夺与真实乘员移交，各阶段可独立验证。
3. 再接步兵武器组合、军官车队、车库补给与原生有限派发，最后完成双加载器及两进程恢复验证。

下一步由实施者按[实施计划](../plans/2026-10-25-prototype-ground-vehicles.md)执行。当前原作外观目视仍有缺口，应明确补齐；它不允许把设计文字标成载具已完成。
